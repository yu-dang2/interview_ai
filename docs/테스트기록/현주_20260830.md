담당 파트인 `agent/graph/`(LangGraph 워크플로우·라우팅)와 `agent/retrieval/`(직무 지식 카드 RAG) 기록이다.
6/13 그래프 조립부터 8/25 로딩 단축까지, **1부는 설계와 그때 돌린 검증**, **2부는 실 LLM 측정**으로 나눠 적었다.

별도 표기가 없으면 로컬 `.venv`(Python 3.12.9)에서 실 LLM(gpt-5-mini)으로 돌렸고,
`mock` 이라고 적은 것은 LLM 스텁으로 돌린 결정적 테스트다.

```
모델 기본          gpt-5-mini (기본 reasoning 이 이미 medium)
파싱(resume)       gpt-4o-mini
매칭               gpt-5-mini + reasoning_effort=low
임베딩             text-embedding-3-small
검색 임계값         KNOWLEDGE_MAX_DISTANCE=0.60, max_results=2
```

# 1부 · 그래프 설계

## 0. 현재 구조

노드 10개 + 조건부 라우터 2개. 라우터는 **노드가 아니라서 LLM 을 부르지 않고** State 값만으로 분기한다.

```
[시작 — 파싱과 검색이 병렬]
  START                                  → persona_selector
  persona_selector                       → jd_parser, resume_parser              (fan-out)
  jd_parser                              → jd_resume_matcher, question_retriever (fan-out)
  resume_parser                          → jd_resume_matcher
  jd_resume_matcher, question_retriever  → question_generator                    (fan-in)

[질문 생성 후 — question_router]
  is_finished (종료 주입 / 질문 소진)     → report_generator
  그 외                                  → answer_evaluator (interrupt 모드) / END

[답변 평가 후 — topic_router]
  is_finished 또는 turn_count >= 10      → report_generator
  현재 질문이 라포                        → question_generator      (꼬리질문 안 붙임)
  70점 미만 이면서 꼬리 < 2               → follow_up_generator → answer_evaluator (순환)
  그 외                                  → question_generator

[종료]
  report_generator → resume_optimizer → END
```

| 구분 | 이름 | 하는 일 |
|---|---|---|
| 노드 | `persona_selector` | 면접관 페르소나 확정 (기술 리드 / 인사 담당자 / 임원 면접관) |
| | `jd_parser` · `resume_parser` | 원문 → 구조화. **병렬**(fan-out) |
| | `jd_resume_matcher` | 적합도 `match_score` + `interview_topics` 산출 |
| | `question_retriever` | 직무 지식 카드 검색(RAG). **매칭과 병렬** |
| | `question_generator` | 질문 5~6개 일괄 생성 (첫 질문은 라포) |
| | `answer_evaluator` | 답변 채점 |
| | `follow_up_generator` | 꼬리질문 생성 |
| | `report_generator` | 최종 리포트 |
| | `resume_optimizer` | 이력서 첨삭 제안 |
| 라우터 | `question_router` | 질문 생성 후: 소진/종료 주입이면 리포트, 아니면 계속 |
| | `topic_router` | 답변 평가 후: 리포트 / 꼬리질문 / 다음 질문 |

**분기 상수** (`edges/topic_router.py`)

```
THRESHOLD        70   70점 미만이면 꼬리질문
MAX_FOLLOW_UPS    2   한 주제 최대 3문항 (주질문 1 + 꼬리 2)
MAX_TURNS        10   전체 턴 상한
```

**State 채널 설계** — 이 구분이 나중에 리포트 총점 버그의 원인이 됐다(2부 §8).

| 종류 | 채널 | 동작 |
|---|---|---|
| 누적(리듀서 `add`) | `eval_keywords` · `weakness_areas` · `eval_results` | 면접 전체에서 쌓인다 |
| `add_messages` | `messages` | 대화 전체 |
| LastValue | `eval_score` · `eval_result` · `retrieved_knowledge` 등 | **마지막 값만** 남는다 |

`retrieved_knowledge` 가 LastValue 인 건 의도한 것이다. 순환 경로로 재진입할 때 `question_retriever` 가
스케줄되지 않아 **첫 검색 결과가 그대로 유지**되고 재검색이 일어나지 않는다.

## 1. 초기 조립 (6/13 ~ 7/10)

노드 8개 + `topic_router` + 실행 루프를 **커밋 하나에 노드 하나씩** 올렸다(`c4104f7` ~ `4aa838e`).
State 를 먼저 정의하고 노드를 붙이는 순서로 갔다 — 노드끼리 직접 값을 주고받을 수 없고 반드시 State 를 거치므로
스키마가 먼저 서야 노드 시그니처가 고정된다.

이 단계에서 잡은 것들.

| 항목 | 내용 |
|---|---|
| `add_messages` → `operator.add` (`6023d32`) | `eval_keywords`·`weakness_areas` 에 `add_messages` 를 쓰고 있었다. 이건 **메시지 객체용 리듀서**라 평범한 문자열 리스트에는 맞지 않는다. `operator.add` 로 교체 |
| `THRESHOLD` 70 (`0be2466`) | 예진님 평가 점수 체계가 0~100 으로 확정되면서 반영 |
| `MAX_TURNS` 5 → 10 (`ef23ed9`) | 세션이 너무 빨리 끝났다 |
| import 절대경로 통일 (`062fd75`) | 상대 import 가 섞여 있어 실행 위치에 따라 깨졌다. `agent.` 절대경로로 10개 파일 정리 |
| 페르소나 v2 반영 (`44c72e1` 외 3건) | 예진님 프롬프트 v2 로 `PERSONA_MAP` 키·변수명·`eval_score` 키가 바뀐 걸 따라감 |

**여기서 나온 교훈이 이후에 계속 반복된다** — 프롬프트(예진님)와 그래프(나)가 키 이름으로 계약을 맺고 있는데,
한쪽만 바뀌면 조용히 깨진다. `.get()` 기본값 때문에 예외도 안 난다. (2부 §6에서 실제로 또 터진다)

## 2. async 전환과 `call_llm` 신뢰성 (7/21, `4606efd`)

FastAPI 에 올리려면 이벤트 루프를 막으면 안 되므로 `OpenAI` → `AsyncOpenAI`, 노드 8개를 전부 `async def` 로 바꿨다.
같이 `call_llm` 의 예외 처리를 보강했다.

| 항목 | 설계 |
|---|---|
| 재시도 | 최대 3회, 지수 백오프 1→2→4초 |
| 잡는 예외 | `openai.OpenAIError`(네트워크·rate limit·타임아웃을 전부 상속) + `json.JSONDecodeError` |
| 최종 실패 | 원인을 `__cause__` 에 물린 `RuntimeError`. **조용한 `None` 반환 금지** |
| 코드펜스 | ` ```json ... ``` ` 제거를 `_clean_json_text()` 헬퍼로 분리 |
| 시그니처 | 뒤에 기본값 인자만 추가 → 노드 호출부 수정 불필요 |

**검증(mock)** — 코드펜스 제거, 순수 JSON, **API 에러 2회 후 성공(실측 3.0초 = 1+2초)**, JSON 깨짐 후 성공,
3회 전패 시 `RuntimeError`(+`__cause__`), `max_retries=1` 동작 전부 통과.

이때 미해결로 남긴 것 — **`jd_parser` 노드만 async 인데 내부 `parse_jd_from_text()` 는 동기 `OpenAI`** 라
이벤트 루프를 블로킹한다. `agent/parsers/` 는 수정 금지 영역이라 지금도 열려 있다(2부 §10에서 로딩 22초로 정량화됨).

## 3. `build_graph` 팩토리와 checkpointer 전환 (7/21 ~ 7/22, `fb07264` `6d0e2da`)

### output 스키마가 CLI 루프를 깨뜨리고 있었다

백엔드와 합의한 `output=InterviewOutput` 때문에 `ainvoke()` 반환값이 output 키(`messages`, `is_finished`,
`report_result`)로 **필터링**되면서 `question_list`·`match_result` 가 유실됐다. 다음 턴 `question_generator` 가
빈 `question_list` 로 재생성 분기를 타 `state["match_result"]` 에서 KeyError. FastAPI 쪽은 무해하지만
CLI 테스트 경로는 첫 답변에서 터졌다.

선택지가 둘이었다.

| 안 | 내용 | 판단 |
|---|---|---|
| ① `output=` 제거 | 간단 | 백엔드 합의사항을 되돌린다 |
| ② **checkpointer + `thread_id`** | FastAPI 에 어차피 필요 | **채택** — 합의를 보존하면서 원인을 없앤다 |

### 설계

- `build_graph(checkpointer=None, interrupt_before=None)` — **HITL 을 opt-in 파라미터로.**
  `interrupt_before` 가 주어질 때만 `question_generator → answer_evaluator` 엣지를 추가하고
  `compile(interrupt_before=["answer_evaluator"])`. 기본값에선 기존 토폴로지 유지 → 백엔드 무영향.
- 모듈 레벨에 `graph = build_graph()` 유지 → 기존 `from ... import graph` 사용처가 그대로 동작.
- `agent/graph/__init__.py` 에 `load_dotenv(find_dotenv())` 배치. 패키지 `__init__.py` 는 하위 모듈 import 시
  항상 먼저 실행되므로 **어떤 모듈로 진입하든, cwd 가 어디든** 환경변수 로딩이 보장된다.

### 답변 주입 방법을 한 번 틀렸다

초안은 `invoke({"current_answer": ...})` 였는데 틀렸다. (a) **어떤 노드도 `current_answer` 를 읽지 않고**
`answer_evaluator` 는 마지막 `HumanMessage` 를 읽으며, (b) `input=InterviewInput` 스키마가 invoke 입력을 필터링한다.

올바른 방법은 `aupdate_state(config, {"messages":[HumanMessage(...)]})` (스키마 우회 + `add_messages` 리듀서로 append)
후 `ainvoke(None, config)` 재개다. State 는 항상 `aget_state()` 로 읽어 output 필터와 무관하게 온전하다.

### 부수 효과 — 버그 하나가 저절로 잡혔다

기존 구조는 꼬리질문 생성 후 **사용자 답변 없이** 같은 답변을 재평가하며 `follow_up_count` 가 3이 될 때까지 돌았다.
`answer_evaluator` 직전 정지로 "질문 후 답변 대기"가 되면서 자연 교정됐다.

**검증(mock)** — before/after 로 KeyError 재현→해소, 70↑ 다음질문 / 70↓ 꼬리질문(대기) / 10턴 종료 **4시나리오 통과**.

## 4. 백엔드 연동 4건 (7/22)

인터페이스 합의가 끝나 확정된 4건. **공통 제약** — 프롬프트는 전부 `agent/parsers/`(수정 금지 영역)에 있어서
"프롬프트에 지시 추가"는 **노드 안에서 기존 프롬프트 상수에 보충 문자열을 이어붙이는 방식**으로 구현했다.
이 우회법을 여기서 처음 쓰고 이후 계속 재사용한다.

| 작업 | 설계 | mock |
|---|---|---|
| `is_finished` 조건부 엣지 (`6d0e2da`) | `question_generator` 나가는 엣지를 `question_router` 로 조건부화. 질문 소진 시 dead-end 대신 리포트로 연결 | 11 |
| `report_generator` 엣지케이스 (`f4dcadb`) | 답변 0개(=`messages` 의 `HumanMessage` 수)면 **LLM 미호출** 고정 문구. 답변 1+면 중도 종료 여부를 **코드로 판정**해 명시 전달 | 13 |
| `match_score` (`74bf863`) | 적합도 0~100 정수. `int` 변환 + 클램핑, 실패 시 기본값 0 | 15 |
| STT/TTS 스텁 (`9cbbe74`) | async 시그니처 + `NotImplementedError`(실수로 연결하면 조용한 no-op 대신 즉시 실패) | 9 |

CLI 회귀 18 유지. `match_score` 방어코드는 `150→100`, `-5→0`, `"high"→0`, `None→0` 으로 확인했다.

"답변 수 판단 기준"을 `HumanMessage` 수로 정한 이유 — State 에 `topic_scores` 가 없고 `turn_count` 는 질문 수라 부적합하다.

같이 모델을 `gpt-4o` → **`gpt-5-mini`** 로 바꾸고 `temperature=0` 을 제거했다(`6b88306`). gpt-5-mini 는
temperature 를 지정하면 에러가 난다.

## 5. 종료 경로 · 다이어그램 정확도 · STT/TTS 이관 (7/22 ~ 7/23)

### 중도 종료 세션에 리포트가 안 남았다 (`6836c08`)

`is_finished` 는 라우터 둘이 나눠 처리하는데 **`topic_router` 쪽만 `END` 로 직행**하고 있었다.
백엔드가 종료를 주입하면 `answer_evaluator` → `topic_router` → `END` 로 빠져 `report_generator` 를 건너뛰었다.

"abandoned 세션도 리포트 저장 대상" 합의에 따라 `return END` → `return "report_generator"` (한 파일 +6/-3).
`report_generator` 노드는 **무수정** — 중도 종료 여부를 노드가 직접 재판정하고 답변 0개 경로도 이미 처리되므로
어느 분기로 들어와도 올바르게 나온다(§4 작업2의 설계가 그대로 재사용됐다).

`MAX_TURNS` 분기와 합치지 않았다. 타깃은 같지만 턴 초과는 정상 종료, `is_finished` 주입은 중도 종료로
**결과 리포트가 다르고**, 합치면 향후 abandoned 전용 분기 여지가 사라진다.

### mermaid 에 순환 경로가 통째로 빠져 있었다 (`360cd5b`)

수정 후에도 다이어그램에 `answer_evaluator → END` 가 남아서 파고들었더니, 실제 경로가 아니라
**path map 없는 conditional edge 의 렌더링 폴백**이었다.

`add_conditional_edges` 에 path map 을 생략하면 LangGraph 가 분기 대상을 정적으로 알 수 없어
`answer_evaluator → __end__` 한 줄만 그려지고 `follow_up_generator`·`question_generator` 로 가는
**실제 순환 경로가 통째로 누락**된다. 런타임은 정상이고 도달성 검증도 통과한다(branch 를 "모든 노드로 갈 수 있음"으로 취급).

**대조군으로 확정했다** — `END` 를 반환할 수 없는 라우터(`lambda s: "b"`)만 가진 최소 그래프를 만들었더니
거기서도 `a → __end__` 가 그려졌다. path map 을 명시하니 3개 분기 + 순환 엣지가 모두 표시되고 폴백은 사라졌다.

### STT/TTS 를 그래프 밖으로 (`d6bb923`)

백엔드 합의가 "STT/TTS 는 그래프 밖 API 에서 처리, 그래프는 텍스트만 주고받음"으로 확정돼 §4에서 넣은 스텁을 걷어냈다.

**삭제 전 전역 grep** — 이 노드·필드를 참조하는 코드가 세 파일(스텁 2개 + `state.py`) 밖에 전무해서
팀 통보 없이 제거했다. 대신 `input_type: "text"|"voice"` 를 추가하고, `answer_evaluator` 가 `"voice"` 일 때만
음성 안내 문구를 프롬프트에 이어붙이게 했다. 미지정/`"text"` 면 프롬프트가 **바이트까지 기존과 동일**하다.

**검증(mock)** — §5.1·5.2 로 29항목(라우터 4분기, `is_finished` 주입 통합, 컴파일 그래프 엣지 대조, 폴백 정체 규명),
§5.3 으로 24항목(voice/text 프롬프트 동일성, 두 주입 경로, 삭제 스모크, 회귀) 통과.

## 6. `resume_optimizer` 노드 추가 (8/6, `6b094f4` `bb0c525`)

### 착수 전 조사 — 껍데기만 있었다

| 계층 | 상태 |
|---|---|
| 프롬프트 | `RESUME_OPTIMIZER_SYSTEM_PROMPT` 정의는 있으나 **어디서도 호출되지 않는 dead prompt** |
| 프론트 | 화면은 있으나 키워드·제안이 **하드코딩 상수**, 버튼은 목업 |
| 백엔드 | `optimize`/`apply`/`download` 라우트가 전부 `# TODO` + `pass` |
| 세션 영속화 | 백엔드가 세션을 메모리 dict 에만 두고 종료 시 `del` → **종료 후 재료 재조회 불가** |

**그래서 "화면 진입 시 생성"이 아니라 "면접 종료 시 자동 생성"으로 정했다.** 그 시점에는 재료가 State 에 다 살아있고,
나중 생성은 (아직 없는) 세션 영속화에 의존하게 된다.

### 설계

- `report_generator` 다음에 실행되므로 `report_result` 가 이미 있다 → 전체 대화록 재전송 대신
  **`summary` + `eval_keywords` + `weakness_areas` 를 재사용**(토큰 절약·환각 억제).
- **필드명 정규화** — 프롬프트 파일을 못 고치므로 노드에서 화면·DB 키로 변환. 각 제안에 `id`(`opt-1`…)를 부여해
  프론트가 개별 "적용"을 고를 수 있게 했다.
- `report_generator → END` 를 `report_generator → resume_optimizer → END` 로 교체. `report_generator` 가
  END 직전 유일 노드라 **interrupt / non-interrupt 양쪽 토폴로지 공통 경로**다 — 한 곳만 바꿔 둘 다 커버.
- **실패 격리** — 리포트는 성공했는데 최적화만 실패해도 면접 전체가 실패하면 안 된다. `try/except` 로
  `{"matched_keywords": [], "suggestions": []}` 반환 + `logging.error`, 그래프는 정상 END.
- **답변 0개면 LLM 미호출** — 화면 설명이 "면접 답변 기반"이라 근거 없이 문구를 생성하면 환각 위험.

**검증(mock) — 38 통과.** 키 정규화·`id`·실패 폴백·0답 스킵·비-dict 방어, 양쪽 토폴로지 엣지 대조,
통합(정상 종료→리포트+최적화 / 중도 0답→빈 최적화 / 최적화 실패→면접은 정상 END), 회귀 전부.

## 7. 파싱 병렬화 (8/10, `399a4ef`)

`jd_parser` → `resume_parser` 가 **직렬**로 연결돼 있어 두 LLM 호출 시간이 그대로 더해지고 있었다.
두 노드는 서로의 결과를 쓰지 않는다(각각 `jd_raw`/`resume_raw` 만 읽고 `jd_parsed`/`resume_parsed` 에만 쓴다).

`persona_selector` 에서 fan-out 하고 `jd_resume_matcher` 로 fan-in 하도록 바꿨다.
반환 State 키가 겹치지 않아 **리듀서 없이도 쓰기 충돌이 없다.**

| | 변경 전 | 변경 후 |
|---|---|---|
| 파싱 구간 | 34.6초 | **17.5초** |
| 면접 시작 전체 | 122.9초 | 약 107초 |

(체크포인트 DB 기록 5개 세션 기준)

fan-in 대기는 LangGraph 가 보장한다 — 부모가 둘이면 두 파서가 같은 super-step 에 스케줄되므로
그 step 이 끝나야 matcher 가 열린다. **한쪽만 끝난 상태로 matcher 가 먼저 도는 일은 없다.**

**검증(mock) — 49 PASS / 0 FAIL.** 양쪽 토폴로지의 정지 지점과 State 채움, `topic_router` 분기,
`report_generator`, `resume_optimizer`, CLI 루프 회귀.

## 12. 페르소나 편향 — 인사·임원에 기술 질문이 나오는 문제 (8/17~18)

프롬프트는 이미 한계까지 강했다(`PERSONA_HR:53` *"기술 질문은 절대 하지 마세요"*,
`question_generator_prompt.py:47-51` *"★ 매우 중요"*). 그런데도 새어나와서 실측했다.

동일 입력(백엔드 JD + 이력서), 페르소나 3종 × RAG 유무로 6회 생성.

| 페르소나 | RAG 없음 | RAG 있음 |
|---|---|---|
| 기술 리드 | 기술 4/5 | 4/5 |
| **인사 담당자** | **기술 2/5** | 0/5 |
| **임원 면접관** | **기술 3/5** | **3/5** |

`interview_topics` 분포는 3종 모두 **기술 6 : 인성 1** 로 동일했다.

**더 나쁜 것 — `type` 라벨 위장.** 인사+RAG 는 `기술 0/5` 로 깨끗해 보이지만 실제 소재는 이렇다.

| # | 라벨 | 소재 |
|---|---|---|
| 2 | 인성 | "800ms→120ms 개선, 어떤 **문제를 먼저 파악**했는지" → 기술 |
| 3 | 인성 | "**MySQL 인덱스 재설계**, 그 **분석 절차**" → 기술 |
| 5 | 인성 | "일 500만 요청 확장, 무엇을 **점검**하고" → 기술 |
| 4 | 인성 | 신입 온보딩·코드리뷰 → 유일한 진짜 인성 |

**LLM 이 소재는 두고 `type` 만 갈아끼웠다. `type` 카운트로 검증하면 문제를 놓친다.**

원인은 프롬프트가 아니라 `jd_resume_matcher` 였다. 페르소나 전달 경로를 감사했더니 8개 노드 중 상류가 전부 미인지였고,
그중 `jd_resume_matcher` 는 `{jd, resume}` 만 받아서 **인사 면접인지 모르는 채 면접 주제를 뽑고 있었다.**
6회 생성 내내 인성 질문 소재가 똑같이 하나(멘토링)였던 게 결정적 증거다 — 인성 topic 이 1개뿐이라 쓸 재료가 그것밖에 없었다.

**수정 후 재측정** (matcher 에 페르소나 전달 + 인사/임원에만 "인성 4개 이상, 기술 2개 이하" 지시)

| 항목 | 수정 전 | 수정 후 |
|---|---|---|
| `interview_topics` (기술 리드) | 기술 6:1 | 기술 5~6:1 (유지) |
| `interview_topics` (인사) | 기술 6:1 | **기술 2 : 인성 5** |
| `interview_topics` (임원) | 기술 6:1 | **기술 2 : 인성 5** |
| 생성 질문 기술 비율 (인사) | 2/5 | **0/5** |
| 생성 질문 기술 비율 (임원) | 3/5 | **1/5** |

인사·임원 **4회 연속** 기준 통과. 인성 소재도 1가지 → 5가지(협업·갈등·멘토링·학습·지원동기)로 늘었고,
라벨 위장은 인사 5개 전부 진짜 인성, 기술 2개는 정직하게 `type="기술"` 로 나왔다.
"균형있게" 같은 정성 표현 대신 **최소 개수를 숫자로** 지정한 게 컸다(정성 표현은 이미 실패 전례가 있었다).

**`match_score` 회귀는 통제 비교로 무혐의**

| | 값 | 평균 | 폭 |
|---|---|---|---|
| 수정 전 재현(persona 없음) ×4 | 87, 88, 85, 88 | 87.0 | 3 |

## 13. 라포(자기소개) 질문이 일반 질문처럼 채점되던 문제 (8/20~21)

프롬프트에 첫 질문을 라포 질문으로 두는 규칙이 들어갔는데 **그래프가 `type` 을 안 읽고 있었다.**
`state.py` 주석이 *"그래프는 아직 type 으로 분기하지 않는다"* 고 스스로 기록해두고 있었다.

"LLM 이 알아서 봐주지 않나?"를 확인하려고 실 LLM 으로 완주시켰다.
백엔드 JD + 이력서, 페르소나 기술 리드, 자기소개에 `"네 안녕하세요 잘 부탁드립니다"` 로 답변.

| 측정 항목 | 값 |
|---|---|
| 생성된 `question_types` | `['자기소개','기술','기술','기술','기술','인성']` (프롬프트대로) |
| 자기소개 `eval_score` | **35** (THRESHOLD 70 미만) |
| 세부 점수 | logic 30 / comm 25 / **expertise 20** / attitude 60 / **problem_solving 20** |
| 실제 라우팅 | **`follow_up_generator`** |
| 생성된 꼬리질문 | "현재 직책과 총 경력 몇 년인지, 담당 업무를 한 문장으로 말씀해 주시겠어요?" |
| `question_feedbacks` | 6개, 첫 항목이 자기소개(40점) |
| `total_score` | 66 (B) |

평가 피드백 원문 — *"답변이 매우 짧아 면접 질문의 핵심을 전혀 담고 있지 않습니다 … 기술적·경험적 근거가 전혀 없어 평가가 낮습니다."*

**자기소개에 전문성 20점, 문제해결력 20점을 매겼다.** 긴장 풀라고 던진 첫 질문에 곧바로 추궁이 붙었고,
그 한 문항이 16턴 중 2턴과 `MAX_TURNS=10` 예산을 잡아먹었다.

수정은 4개 지점(채점 스킵 / 꼬리질문 가드 / 리포트 집계 제외 / 누적 채널)에 넣었고 설계 원칙을 둘 정했다 —
**인덱스 폴백을 두지 않는다**(`type` 만 본다. "첫 질문이면 자기소개"를 넣으면 프롬프트가 `type` 을 빠뜨려도 조용히 넘어가 회귀를 놓친다),
**`question_list` 를 코드로 필터링하지 않는다**(질문-답변 정렬이 위치 기반이라 하나만 빼면 통째로 밀린다. 대신 "집계에서 빼라"고 지시만 한다).

**수정 후 재측정** (동일 하네스·동일 시나리오)

| 측정 항목 | 수정 전 | 수정 후 |
|---|---|---|
| 자기소개 `eval_score` | 35 | **80** (중립) |
| 자기소개 LLM 채점 호출 | 있음 | **없음** (`eval_detail={}`, `feedback=''`) |
| 자기소개 뒤 라우팅 | `follow_up_generator` | **`question_generator`** |
| `question_feedbacks` 내 자기소개 | 있음 (40점) | **없음** |
| `category_scores` | expertise 70 / problem_solving 66 | expertise 70 / problem_solving 71 |
| 총 턴 수 | 16턴 | **10턴** |

라우터 단위 회귀도 같이 봤다 — 기술 질문 + 35점 → `follow_up_generator`(기존 유지),
자기소개 + 35점 → `question_generator`, `index == len(question_list)` → IndexError 없음,
`is_finished`·`turn_count=10` → `report_generator`(우선순위 유지).

### ⚠️ 이 표에서 점수 비교는 무효다

측정 하네스가 답변 풀을 **턴 순서(`len(turns) % 5`)로 로테이션**했는데, 자기소개가 2턴을 덜 먹으면서
어떤 답변이 어떤 질문에 가는지가 통째로 밀렸다. `total_score` 66→71 은 답변-질문 궁합이 우연히 좋아진 것이지
코드 개선 효과가 아니다.

- ❌ 신뢰 불가: `total_score`, 비-자기소개 질문 점수 비교
- ✅ 유효: 자기소개 점수·라우팅·`question_feedbacks` 포함 여부(답변 품질과 무관한 구조적 사실), 라우터 단위 검증

이후 프롬프트 쪽에서 `type` 값이 `"자기소개"` → `"라포"` 로 바뀌어(PR #73) 그래프 분기도 `RAPPORT_TYPE` 으로 따라갔다.
`git pull` 은 현재 브랜치의 upstream 만 갱신하는데 변경이 `feature/prompt` → `develop` 으로 가서
`feature/langgraph` 에는 없었고, `main` 은 더 옛날 값(`"기술 or 인성"`)이었다. 브랜치별 실제 값을 하나씩 확인해서야 파악됐다.

## 14. 종료 판정 — 정상 완주가 "중도 종료"로 표기되던 버그 (8/18)

`report_generator.py:62` 의 `is_early_terminated = turn_count < MAX_TURNS` 가 **항상 True** 였다.
`turn_count` 는 주 질문에서만 +1 하고 꼬리질문은 안 세는데 본질문이 5개라 10을 못 넘는다.
**15턴을 답해도 `turn_count`=5** 로 재현됐다.

질문 소진 여부(`current_question_index` vs `len(question_list)`)로 판정하도록 바꿨다.
`question_generator` 는 소진 시 인덱스를 `len(question_list)` 로 올리고, 종료 버튼은 `question_generator` 를
거치지 않아 `index < len` 이 유지되므로 **두 경로가 구조적으로 구분된다.**

| 시나리오 | index/len | 수정 후 | 수정 전 |
|---|---|---|---|
| 정상 완주 | 5/5 | **False** | True ← 오탐 |
| 중도 종료 (3번째) | 2/5 | True | True |
| 중도 종료 (마지막 직전) | 4/5 | True | True |
| 중도 종료 (첫 질문) | 0/5 | True | True |
| 답변 0개 | — | True | True |

DB 스키마를 고친 뒤 실데이터로도 확인했다 — 중단됐던 세션(`index 3/7`) 종료 재시도에서
`status=finished`, `total_score=79`, `is_early_terminated=True` 로 정상.

**"리포트가 생성 안 된다"의 진짜 원인은 DB 스키마 불일치였다.** 그래프는 정상이었고(두 시나리오 모두 리포트 생성 확인)
체크포인트 유실도 없었다(세션 5건 전부 존재). 실제로는 `interview_results` 테이블에 모델에는 있는데
**DB 에 없는 컬럼이 12개**였다. `Base.metadata.create_all()` 은 없는 테이블만 만들고 기존 테이블 컬럼은 안 고친다.
DROP 시 FK 순서도 팀 안내와 달랐다 — 자식이 하나가 아니라 둘(`interview_question_feedbacks` 가 누락돼 있었다).

같이 확인한 것 — 꼬리질문 상한을 3 → 2 로 줄여 **한 주제 최대 4문항 → 3문항, 면접 전체 최대 20문항 → 15문항**.
전부 70점 이상이면 5문항인 건 변함없다.

## 15. 리포트 총점이 실시간 평가와 어긋나던 문제 (8/24)

유정님 피드백 *"report_generator 가 LLM 한테 eval_score 를 안 넘겨서 재채점하고 있다"* 를 확인한 결과 정확했다.

payload 에 들어가던 건 `question_list` / `conversation`(텍스트만) / `eval_keywords` / `weakness_areas` /
`is_early_terminated` 뿐이고 **점수는 한 번도 실리지 않았다.** 그런데 프롬프트는 *"각 답변의 평가 결과를 종합·평균하라"* 고
**있다고 전제하고 지시**한다. 원인은 §0에 적은 채널 종류였다 — `eval_score`·`eval_result` 는 리듀서 없는 `LastValue` 라
**마지막 답변 것만** 남는다. 누적 리듀서가 붙은 건 `eval_keywords`·`weakness_areas` 둘뿐이었다.

`eval_results` 누적 채널을 새로 만들면서 세 가지를 정했다.

- **점수 필드만 추린다** — `feedback`·`follow_up_focus` 까지 넣으면 프롬프트가 비대해지고 리포트에 엉뚱하게 반영된다.
- **질문 텍스트는 마지막 `AIMessage` 에서 가져온다** — `question_list[current_index]` 를 쓰면
  꼬리질문 답변에 주질문 텍스트가 붙는다.
- **빈 `eval_results` 는 payload 에서 키 자체를 뺀다** — 빈 배열을 주면서 "평균하라"고 하면 모델이 없는 값을 짜맞춘다.

**실 LLM A/B** (실시간 점수 `[55, 48, 60]`, 평균 54.3)

| | 수정 전 | 수정 후 |
|---|---|---|
| `total_score` | 64 (오차 **9.7**) | **54** (오차 **0.3**) |
| `category_scores` 평균 | 69.4 (오차 15.1) | **54.6** (오차 0.3) |
| `question_feedbacks` 개수 | 2 | **3** |
| 개별 점수 | `[65, 62]` | `[55, 48, 60]` (실시간과 일치) |

**부수 효과** — `question_feedbacks` 개수가 런마다 흔들리던 문제가 여기 연결돼 있었다.
`interview_service.py:519` 는 실시간 점수 개수와 `question_feedbacks` 개수가 **같을 때만** 점수를 바꿔 끼우는데,
LLM 이 꼬리질문을 별도 항목으로 안 내면 어긋나서 보정이 통째로 포기됐다. `eval_results` 를 넘기니 개수가 맞아떨어져
그 경로가 살아났다. 다만 **LLM 재량이라 항상 보장되지는 않는다.**

검증은 스텁으로 그래프 전체를 돌린 결정적 테스트 13항목(라포 제외·꼬리질문 포함·전체 누적·`order` 연속·세부 5종)
+ 회귀 9항목(꼬리질문 없는 완주 / 답변 0개 / **구 체크포인트 호환**) 통과.
이 변경 전에 시작된 세션은 체크포인트에 `eval_results` 가 없어 수정 전과 동일하게 동작한다.

## 17. 모델·reasoning 조합 A/B — 로딩 27% 단축 (8/24~25)

예진님(질문생성 `low` + 파싱·매칭 `gpt-4o-mini`, "로딩 절반")과 유정님(파싱·매칭만 `low`, 질문생성은 유지, "20~35초 단축")의
제안이 **"질문생성을 low 로 해도 되는가"** 에서 갈려서 데이터로 판정했다.

착수 전 조사에서 `reasoning_effort` 는 프로젝트에 **0건**이었다(API 기본값으로 돌고 있었다).
`call_llm` 하나가 LLM 노드 7개의 공통 통로라 거기만 고치면 되지만 **`jd_parser` 는 이 통로를 지나지 않는다** —
예진님의 `parse_jd_from_text()` 가 자체 클라이언트로 호출한다. 로딩의 약 22초를 차지하는데 우리가 못 바꾼다.

실험 장치는 `reasoning_effort` 가 `None` 이면 **`create()` 에 키 자체를 넣지 않게** 만들었다.
그래야 아무것도 설정하지 않은 환경에서 기존과 **바이트 단위로 동일한 요청**이 나가고 회귀 위험이 0이 된다.

### ⚠️ 1차 측정 무효 — 시간 드리프트

4개 조합(A 현행 / B 전부 low / C 질문만 유지 / D 전부 low)을 A→B→C→D 순으로 5회씩 돌렸는데,
**B와 D는 측정한 3단계에서 설정이 완전히 동일한데** 중앙값이 46.4s vs 67.8s 로 21.4초 차이 났고 범위가 아예 겹치지 않았다
(B 42.7~49.0 / D 67.4~76.7).

조합 **내부** 편차는 작은데 조합 **간**에만 큰 차이 → API 지연이 시간대에 따라 흔들린 게 조합 효과로 잘못 잡힌 것이다.
**동일 설정 대조군을 넣어두지 않았다면 못 잡았을 오류다.** 한 라운드 안에서 설정을 번갈아 재는 교차 실행으로 재측정했다.

### 교차 실행 재측정

| 단계 | 기본 | low | medium |
|---|---|---|---|
| `resume_parser` | 17.9s | **8.9s** | — |
| `jd_resume_matcher` | 36.6s | **24.8s** | — |
| `question_generator` | 27.9s | **14.2s** | **27.4s** |

`qgen/medium` 27.4s ≈ `qgen/기본` 27.9s — **`gpt-5-mini` 의 기본 reasoning 이 이미 medium 이다.**
즉 "질문생성을 medium 으로 낮춘다"는 사실 **"손대지 않는다"** 와 같고 설정을 넣을 필요조차 없다.

두 분 수치는 각자 자기 조합에서 재현됐다 — 유정님 "20~35초"는 C 조합에서 21.3초, 예진님 "절반"은 B 조합에서 42%.

### 질문 품질 — 각 조합 30문항(5회 × 6문항), 동일 LLM 심사자

| 조합 | 개념 ≥3 | 물음표 누락 | 한 문장 2질문 | 재시도 |
|---|---|---|---|---|
| A. 현행 | 9 | 6 | 6 | 0 |
| **B. 질문생성 low** | **10** | **12** | 0 | 0 |
| **C. 질문생성 유지** | **5** | **0** | 0 | 0 |
| D. 전부 low | 10 | 9 | 0 | 0 |

C 가 B 의 절반이다. 13.1초를 더 쓰고 위반을 절반으로 줄이는 거래이고, 음성 면접이라 **유정님 판단이 타당하다.**

단서 두 가지 — ① 유정님 실측(30개 중 1개)보다 훨씬 많이 나왔다. 심사 프롬프트가 더 엄격한 것으로 보이므로
**절대 개수가 아니라 조합 간 상대 비교로만** 읽어야 한다. ② **현행(A)도 이미 9건**이다. low 가 만든 문제가 아니라
원래 있던 문제를 악화시키는 구조다. **[확인 필요]**

`low` 에서 JSON 이 깨져 재시도로 오히려 느려지는 시나리오는 기우였다(4개 조합 전부 0회).

### 모델 교체 시 이력서 파싱 누락 검증 (유정님 요청)

*"모델을 바꾸는 쪽이라 파싱 결과에 항목 누락이 없는지 봐 달라. 거기서 빠지면 매칭부터 질문까지 전부 틀어진다."*

일부러 지저분하게 만든 합성 이력서 5종(날짜 형식 4종 혼용, 불릿 문자 혼용, 표, 섹션 순서 뒤죽박죽, 구어체, 숫자 표기 혼용).

| 이력서 | 정답지 | 현행 | `low` | `gpt-4o-mini` |
|---|---|---|---|---|
| 1. 깔끔한 텍스트 | 15개 | 0 / 13.0s | 0 / 8.1s | **0 / 5.9s** |
| 2. 표·불릿 혼재 | 20개 | 0 / 21.5s | 0 / 9.7s | **0 / 3.7s** |
| 3. 항목 과다·장문 | 43개 | **1** / 29.8s | **1** / 18.1s | **0 / 9.0s** |
| 4. 형식 흐트러짐 | 16개 | 0 / 17.7s | 0 / 9.7s | **0 / 4.4s** |
| 5. 정량 성과 다수 | 26개 | 0 / 22.5s | 0 / 12.4s | **0 / 4.9s** |

**현행 대비 추가 누락 0.** 유일하게 빠진 `성과 12만명` 은 현행(3회 중 1회)과 `low`(3회 중 2회)가 놓치고
`gpt-4o-mini` 는 3회 모두 잡았다 — 예상과 반대다.

`matching_skills` 도 전부 동일했다. R5 에서 `gpt-4o-mini` 만 `REST API 설계` 가 빠져 보였는데
**매칭을 방식당 1회만 돌린 탓**이었고, 3회씩 재측정하니 세 방식 모두 3/3 이었다. 단일 실행 차이를 결론으로 삼을 뻔했다.

### 확정 반영

```
resume_parser      model = gpt-4o-mini       (22.4s -> 5.4s)
jd_resume_matcher  reasoning_effort = low    (45.9s -> 30.2s)
그 외 5개 노드      비워둠 (요청 키가 model, messages 뿐)
```

우선순위는 `<STAGE>` 환경변수 > 전역 환경변수 > `STAGE_DEFAULTS` > 기본값이라 `.env` 로 재배포 없이 조정할 수 있다.

**로딩 120.6s → 87.8s (-27%).** 절대값이 이전 측정(98→73)보다 높은데 두 설정을 같은 라운드에서 번갈아 잰 결과라
**비율은 신뢰할 수 있다.**

지뢰 하나 — `gpt-4o-mini` 는 추론 모델이 아니라 `reasoning_effort` 를 받으면 **400** 이 난다.
두 분 제안을 섞어 "파싱은 gpt-4o-mini + reasoning low" 로 설정하면 면접 시작이 통째로 실패한다.
비추론 모델이면 인자를 빼고 조합당 한 번만 경고를 남기게 했다.

검증은 스텁 클라이언트로 7개 노드가 **실제로 보내는 요청 인자**를 직접 확인(20항목).
안 건드린 5개 노드의 요청 키가 `['messages', 'model']` 뿐임을 확인했다 — `None` 을 넘기는 게 아니라 키 자체가 없다.
회귀는 페르소나 편향(인사·임원 각 3회, 인성≥4·기술≤2) 통과, 리포트 총점 오차 0.3 통과.

⚠️ `gpt-4o-mini` 파싱 검증은 **합성 이력서로만** 했다. PDF/스캔 업로드 경로(`uploads.py` 의 pypdf/docx)를 거친
실제 텍스트로는 확인 못 했다. 글자 붙음·표가 한 줄로 뭉개짐·OCR 오인식이 재현하지 못한 가장 큰 공백이다. **[확인 필요]**

## 18. 30분 제한 진단 — 그래프는 원인이 아니었다 (8/25, 조사만)

*"질문이 30분 끝나기 10초 전에 생성되면 답변을 못 하는 경우가 있다"* 는 증상의 원인을 좁히려고 후보 4개를 추적했다.
코드는 수정하지 않았다.

**`agent/graph/` 전체에 `time`·`datetime` 사용이 0건이다.** 그래프는 30분이라는 개념 자체를 모르고,
답변이 29분에 오든 35분에 오든 똑같이 처리한다.

| 후보 | 결과 |
|---|---|
| 프론트 `_awaitingAnswer` 가 렌더 시점 값 | 재현되지만 **안전한 방향**(질문이 떠 있으면 자동 종료가 안 걸림). 원인 아님 |
| 백엔드 `_asked_within_limit` 가 한 번만 열어줌 | 의도대로 동작. **백엔드는 정상** |
| 기준 시각 어긋남 | 새로고침 시 `iv_start` 와 `session_id` 가 함께 날아가 새 면접이 시작되므로 같은 세션에서 타이머만 어긋나진 않는다 |
| **★ 응답 수신 후 다음 질문을 버림** | **주범** |

`04_면접_진행.py:1298` 의 시간 초과 검사가 **`api.send_answer()` 가 돌아온 뒤** 실행되는데,
그 한 번의 호출에 답변 평가 + 다음 질문 생성 LLM 호출이 들어가 30~60초 걸린다.

```
t=29:20  답변 제출 → 백엔드 통과(29.3 < 30) → 그래프 실행
t=30:10  백엔드가 다음 질문 반환 (DB 에도 정상 기록)
t=30:10  프론트: _iv_time_up = True → resp["next_question"] 을 버리고 즉시 종료
```

**생성까지 끝난 질문이 화면에 뜨지도 못하고 버려진다.** 백엔드는 유예를 구현해뒀는데 프론트가 그 유예를 쓸 기회를 없애고 있다.

반대로 "질문이 29분 50초에 생성된" 경우는 이미 정상 동작한다 — 질문이 뜨고, `_awaitingAnswer` 가 자동 종료를 막고,
`_asked_within_limit` 가 답변을 받아주고, 그 점수는 `eval_results` 에 쌓여 리포트에 반영된다(§15에서 만든 채널이 여기서도 유지된다).

별건으로, 제한 시간 값이 프론트 `30*60` 하드코딩 ↔ 백엔드 `INTERVIEW_TIME_LIMIT_MIN`(env)로 **연결돼 있지 않다.**
`docker-compose.yml` 에서 20으로 바꿔도 화면은 30분을 센다.
