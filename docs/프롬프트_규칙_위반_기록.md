# 프롬프트 규칙 위반 관찰 기록

프롬프트에 명시된 규칙을 그래프 출력이 지키지 않은 경우를 모았다.
LLM 이 규칙을 어겨도 코드가 걸러내지 않아 그대로 면접에 들어간다.

관찰 기간 2026-08-20 ~ 08-27, 컨테이너 환경.

---

## 요약

| # | 위반 내용 | 근거 규칙 | 관측 |
|---|---|---|---|
| 1 | 질문 개수가 6개가 아님 | question_generator 2번 | 10회 중 2회 |
| 2 | 앞 질문과 같은 꼬리질문 반복 | follow_up 6·9번 | 7건 |
| 3 | 한 질문에 개념 여러 개 | follow_up 3번 / question_generator 7번 | low 에서 다수 |
| 4 | 질문 type 오분류 | question_generator 출력 형식 | 1건 |

---

## 1. 질문 개수가 지시와 다름

`question_generator_prompt.py` 2번

```
질문은 맨 앞에 라포 형성 질문 1개를 넣고, 그 뒤에 평가용 질문 5개를 생성하세요. (총 6개)
```

### 관측

| 실행 | 결과 | 최대 문항 |
|---|---|---|
| 스모크 테스트 (8/26) | 라포 1 + 평가 6 = **7개** | 19턴 |
| 경력별 비교 · 주니어 (8/26) | 라포 1 + 평가 4 = **5개** | 13턴 |
| 재현 3회 (8/26) | 6개 | 16턴 |
| 재현 3회 · 같은 입력 (8/26) | 6개 | 16턴 |
| 경력별 비교 · 나머지 3건 | 6개 | 16턴 |

**10회 중 2회가 지시와 다르다.**

### 영향

평가 질문 하나가 늘면 꼬리질문까지 최대 3문항이 늘어난다.

```
평가 5개   라포 1 + 5 x 3 = 16문항
평가 6개   라포 1 + 6 x 3 = 19문항
```

실제로 스모크 테스트가 19턴을 돌았다. 면접 30분 제한이 있어 시간을 넘길 수 있다.

### 코드에서 막히지 않는 이유

`question_generator` 가 LLM 응답의 질문 개수를 확인하거나 잘라내지 않는다.
몇 개가 오든 `question_list` 에 그대로 들어간다.

`topic_router.MAX_TURNS = 10` 이 있지만 `turn_count` 는 주질문에서만 +1 되므로
6~7개 구간에서는 걸리지 않는다.

## 2. 앞 질문과 같은 꼬리질문 반복

`follow_up_prompt.py` 4번 · 6번 · 9번

```
4. 지원자가 "모르겠다"고 했을 때 추가로 물어볼 힌트성 질문도 고려하세요.
6. 답변이 너무 짧거나, 맥락에 맞지 않거나, 모른다는 신호일 때는 더 깊이 파고들지
   마세요. 대신 난이도를 낮춰 답하기 쉬운 힌트성 질문을 하거나, 이 주제를
   마무리하는 방향으로 물으세요.
9. 지원자가 이미 답한 내용은 다시 묻지 마세요. 같은 것을 수치만 더 붙여
   재질문하지 마세요.
```

### 관측 요약

| 출처 | 조건 | 건수 |
|---|---|---|
| 실제 면접 화면 | "모르겠다"로 답변 | 1 |
| 실제 면접 화면 | 정상 답변 (62점) | 1 |
| 전체 면접 1차 | 수치 없는 답변 | 2 |
| 전체 면접 2차 | 키워드 매칭 답변 | 2 |
| 전체 면접 3차 | 수치·근거 포함 답변 | 1 |

**총 7건. 답변 품질과 무관하게 나온다.**

같은 조건으로 4턴을 따로 돌렸을 때는 나오지 않았다. 항상 나오지는 않지만,
안 나온다고 장담할 수도 없다.

### 사례 — 실제 면접 화면, "모르겠다"로 답변

```
[꼬리 질문] 알람 전략은 진행해보지 않으셨다고 하셨는데, 제한된 시간과 자원에서
            우선적으로 어떤 리소스에 알람을 먼저 설정하시겠습니까?

(답변) 해당 부분에 대한 정보가 부족하여 섣부르게 답변을 할 수 없을 것 같습니다.

[꼬리 질문] 제한된 시간과 자원에서 알람을 먼저 설정하신다면 어떤 리소스를
            우선하시겠고 그 선택의 근거는 비즈니스 영향 관점에서 무엇인가요?
```

6번에 해당한다.

### 사례 — 실제 면접 화면, 정상 답변 (62점)

```
[꼬리 질문] 그 프로젝트의 상황과 본인 역할을 상황-과제-행동-결과 흐름으로
            먼저 자세히 말씀해 주시겠어요?

(답변) 팀프로젝트가 아니다 보니 팀원별 역할이 따로 주어져 있지 않았습니다.
       kotlin 으로 안드로이드 To-do 앱을 만들고 백엔드 파트를 자바로 구현하면서...

[꼬리 질문] 그 프로젝트의 구체적 상황과 본인이 맡은 작업 범위와 책임을
            상황-과제-행동-결과 흐름으로 말씀해 주시겠어요?
```

세부 점수가 논리성 58 · 커뮤니케이션 62 · 전문지식 60 · 태도 68 · 문제해결 60 으로
70 미만이라 꼬리질문이 붙었다. 답변이 부실했다기보다 수치가 없어 점수가 낮았다.

### 사례 — 전체 면접 1차, 문장까지 동일

```
2턴  꼬리  API 문서화에 어떤 도구를 사용하셨나요?
3턴  꼬리  API 문서화에 어떤 도구를 사용하셨나요?
```

같은 실행에서 하나 더 나왔다.

```
7턴  꼬리  주문 생성 갱신 취소 같은 도메인 이벤트는 어떤 서비스나 컴포넌트에서
           발행하도록 설계하셨나요?
8턴  꼬리  주문 관련 이벤트는 어떤 서비스가 발행하도록 설계하셨나요?
```

### 사례 — 전체 면접 2차

```
3턴  꼬리  배포 중 자동 롤백은 어떤 모니터링 지표와 임계값으로 트리거되게
           설계하셨나요?
4턴  꼬리  자동 롤백을 어떤 모니터링 지표로, 어떤 임계값과 몇 분 이상 지속될 때
           트리거되도록 설정하셨는지 구체적인 수치로 말씀해 주시겠어요?
```

```
7턴  꼬리  멱등키에 시도 회차를 포함하신 이유와 재시도할 때 결제사와 내부에서
           같은 멱등키를 기대하시는지 각 시나리오별로 설명해 주시겠어요?
8턴  꼬리  멱등키를 주문 아이디와 시도 회차를 조합한다고 하셨는데 같은 재시도에서
           결제사와 우리 시스템에 항상 동일한 멱등키가 전달되도록 어떻게...
```

### 사례 — 전체 면접 3차, 답변에 이미 답이 있는데도 반복

```
5턴  꼬리  재시도마다 시도 회차를 포함한 멱등키를 어떻게 동일하게 보장하셨나요?
6턴  꼬리  멱등키에 시도 회차를 포함한다고 하셨는데 재시도마다 키가 달라지지
           않도록 어떻게 보장하셨나요?
```

5턴 답변에 이미 이렇게 적었다.

```
같은 재시도에서는 메시지에 실린 키를 그대로 쓰기 때문에 결제사와 우리 시스템이
항상 같은 값을 봅니다.
```

9번에 해당한다.

## 3. 한 질문에 개념 여러 개

`follow_up_prompt.py` 3번 · `question_generator_prompt.py` 7번

```
꼬리질문은 짧은 한 문장, 하나의 개념만 담고 물음표로 끝맺으세요.
한 질문에는 핵심 개념 하나만 담으세요.
```

### 관측 (8/20)

`reasoning_effort=low` 로 질문 생성 시

```
가장 큰 병목이 무엇이었고 그 병목을 해결하기 위해 어떤 아키텍처적 변경을 하셨나요
모니터링은 어떤 지표로 했고 장애 대응 사례를 하나 말씀해 주시겠어요?
```

병목 · 아키텍처 변경 · 모니터링 지표 · 장애 사례 네 가지가 한 문장에 들어갔고
중간 물음표가 빠졌다.

### 관측 (8/24, 30문항씩 비교)

| 설정 | 요청 3개 이상인 질문 |
|---|---|
| medium | 0 / 30 |
| low | 1 / 30 |

```
실제 쿼리 튜닝 사례 하나를 설명해 주시겠어요 원래 쿼리 문제는 무엇이었고
어떤 인덱스나 리팩토링을 적용하셨나요 성능이 어떻게 바뀌었나요?
```

`medium` 에서는 관측되지 않았다. 이 결과로 질문 생성은 `medium` 을 유지하기로 했다.

## 4. 질문 type 오분류

`question_generator_prompt.py` 출력 형식

```
"type": "라포 or 기술 or 인성"
```

### 관측 (8/26, 주니어 이력서)

```
[4] type=인성  REST API를 설계하고 문서화할 때 어떤 도구와 절차로 작업하시고
               다른 팀과 어떻게 협업하셨는지 예를 하나 들어 설명해 주시겠어요?
```

도구와 절차를 묻는 기술 질문인데 `인성` 으로 분류됐다.

### 영향

현재는 없다. `type` 은 라포 판정에만 쓰이고 `기술`/`인성` 구분은 코드 어디서도
사용하지 않는다.

```
agent/graph/utils.py:22               라포 판정
backend/services/interview_service.py 라포 판정
```

다만 `follow_up_prompt` 9번이 "인성 질문에는 정량 수치를 강요하지 말라"고 지시하므로,
나중에 그 값을 참조하게 되면 잘못된 기준이 적용될 수 있다.

## 공통점

네 건 모두 **프롬프트에 지시는 있는데 코드가 확인하지 않는** 구조다.

```
질문 개수     개수를 세거나 자르는 곳이 없음
꼬리질문 중복  이미 물어본 질문과 비교하지 않음
개념 나열     생성된 질문을 검사하지 않음
type          값의 타당성을 확인하지 않음
```

LLM 출력은 매번 달라서 프롬프트만으로는 확률만 낮출 수 있다.
같은 조건에서 나올 때도 있고 안 나올 때도 있어, 안 나온다고 장담하기 어렵다.
