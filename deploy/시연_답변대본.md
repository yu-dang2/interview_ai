# 시연 답변 대본

면접 화면에서 질문을 받으면 아래에서 해당 주제를 찾아 말한다.
질문 문장은 매번 조금씩 달라지므로 그대로 읽는 대본이 아니라 주제별 내용 정리다.

이력서·채용공고는 같은 폴더의 `시연_이력서.txt`, `시연_채용공고.txt` 를 업로드한다.

## 측정값 (2026-08-27, 컨테이너 기준)

| 항목 | 값 |
|---|---|
| 면접 시작 로딩 | 약 46초 |
| 답변 처리 | 15~45초, 평균 34초 |
| 리포트 생성 | 약 120초 |
| 답변 턴 | 8회 |
| 결과 | 72점 · B+ |

답변 작성 시간을 턴당 1분으로 잡으면 전체 13~15분이다. 30분 제한 안에 들어간다.

## 왜 이렇게 답해야 하나

채점 프롬프트가 70점 이상을 이렇게 정의한다.

```
70~89점   구체적인 경험과 근거를 포함한 좋은 답변
90~100점  정량적 성과, 의사결정 과정, 대안 비교까지 포함
```

그리고 70점 미만이면 꼬리질문이 최대 2개까지 붙어 면접이 길어진다.
아래 답변들은 네 가지를 의도적으로 넣어 70점을 넘기도록 작성했다.

```
정량 수치    940ms → 180ms, 롤백 5건 → 1건
판단 근거    평소 5xx 가 0.05% 라 그 20배를 임계값으로
대안 비교    카나리도 검토했는데 구성 부담이 커서 롤링을 택함
측정 방법    배포 전후 2주씩 APM 의 p95 를 비교
```

## 주제별 답변

### 1. API 문서화

**이런 질문에** 문서 · OpenAPI · Swagger · 스펙 · 버전 · 문서화

FastAPI 가 만들어 주는 OpenAPI 스펙을 기준으로 삼았습니다. 코드와 문서가 따로 노는 걸 막으려고 스키마를 Pydantic 모델로만 정의하고 문서를 손으로 쓰지 않았습니다. 변경이 있을 때는 스펙 파일을 저장소에 커밋해 PR 에서 차이가 보이게 했습니다. 별도 문서 도구를 쓰는 안도 검토했는데, 문서를 따로 관리하면 반드시 코드와 어긋난다고 판단해 접었습니다. 호환이 깨지는 변경은 버전을 올려 기존 경로를 한 달 유지했고, 그 기간 동안 구버전 호출 비율을 주 단위로 봐서 0.5퍼센트 아래로 떨어지면 내렸습니다. 도입 후 프론트에서 오는 스펙 문의가 주 5건에서 1건 아래로 줄었습니다.

### 2. 쿼리 진단과 p95 개선

**이런 질문에** p95 · 940 · 180 · 느린 · 슬로우 · 튜닝

슬로우 쿼리 로그를 1초 기준으로 켜고 일주일치를 모아 상위 20개를 뽑았습니다. 그중 주문 목록 조회가 전체 느린 쿼리의 62퍼센트였습니다. EXPLAIN 을 보니 회원별 최근 30건을 가져오는데 created_at 단일 인덱스만 있어서 필터 후 정렬에서 filesort 가 걸렸습니다. user_id 와 created_at 복합 인덱스로 바꿔 p95 가 940ms 에서 620ms 로 내려갔고, 그 위에 Redis 캐시를 얹어 180ms 가 됐습니다. 캐시부터 붙이는 안도 있었는데, 쿼리가 느린 채로 캐시를 씌우면 미스가 났을 때 그대로 느려져서 인덱스를 먼저 고쳤습니다. 측정은 배포 전후 2주씩 APM 의 p95 값을 비교했습니다.

### 3. 인덱스 설계

**이런 질문에** 인덱스 · 복합 · 커버링 · 정규화 · 테이블 · 스키마

조회 패턴을 먼저 정리하고 인덱스를 붙였습니다. 주문 목록은 user_id 와 created_at 복합 인덱스, 관리자용 상태별 조회는 status 와 created_at 을 썼습니다. 커버링 인덱스는 목록 조회에만 적용했습니다. 필요한 컬럼이 다섯 개라 전부 넣으면 인덱스 크기가 두 배가 되어, 자주 쓰는 세 개만 포함하고 나머지는 조인으로 가져왔습니다. 전부 넣는 안과 비교했을 때 조회는 15ms 차이인데 쓰기가 8퍼센트 느려져서 안 넣었습니다. 인덱스를 늘릴 때마다 주문 생성 p95 를 같이 재서 5퍼센트 이상 나빠지면 되돌리는 기준을 뒀고, 실제로 한 번 되돌린 적이 있습니다.

### 4. 캐시 설계와 무효화

**이런 질문에** 캐시 · Redis · 무효화 · TTL · 일관성 · 캐시 키

캐시 키는 order:list 뒤에 회원 아이디와 페이지를 붙이는 형태로 잡았고, 단건은 order:detail 뒤에 주문 아이디를 붙였습니다. TTL 은 목록 60초, 단건 10분입니다. 목록은 새 주문이 들어오면 바로 바뀌어야 해서 짧게 뒀고, 단건은 상태 변경이 하루 평균 1.2회라 길게 잡았습니다. 처음에는 TTL 만으로 갔는데 주문 취소 후에도 목록에 남는다는 문의가 월 30건쯤 들어와서, 주문 상태 변경 이벤트를 받아 해당 키를 지우는 방식으로 바꿨습니다. 그 뒤 같은 문의가 0건이 됐습니다. Redis 가 죽으면 DB 로 폴백하되 같은 키 조회는 하나만 DB 로 나가게 락을 걸었습니다. 캐시 적중률은 91퍼센트입니다.

### 5. 이벤트 발행 구조

**이런 질문에** 이벤트 · 발행 · 도메인 · 컴포넌트 · 트리거 · 아웃박스

주문 상태를 바꾸는 주체가 주문 서비스뿐이라 이벤트도 주문 서비스에서만 발행하도록 했습니다. 상태 변경을 저장하는 트랜잭션 안에서 아웃박스 테이블에 이벤트를 같이 쓰고, 별도 발행기가 그 테이블을 읽어 Kafka 로 보냅니다. 처음에는 애플리케이션 코드에서 커밋 직후에 직접 발행했는데, 커밋은 됐는데 발행 직전에 프로세스가 죽으면 이벤트가 유실됐습니다. 월 2~3건 정도 정합성이 어긋나서 아웃박스로 바꿨고 그 뒤 유실은 0건입니다. 소비 쪽은 이벤트 아이디를 키로 처리 여부를 남겨 같은 이벤트를 두 번 받아도 한 번만 반영되게 했습니다.

### 6. Kafka 전환과 멱등키

**이런 질문에** Kafka · 멱등 · 재시도 · DLQ · 파티션 · 큐

결제 실패 즉시 큐에 넣고 1초, 4초, 16초 순으로 지수 백오프 재시도를 합니다. 중복 결제가 가장 큰 위험이라 멱등키를 주문 아이디와 시도 회차로 조합해 결제사에 보내고, 우리 쪽에도 처리 완료 키를 Redis 에 24시간 남겨 두 겹으로 막았습니다. 멱등키는 발행하는 쪽에서 만듭니다. 컨슈머에서 만들면 재시도마다 값이 달라져 의미가 없어서입니다. 같은 재시도에서는 메시지에 실린 키를 그대로 쓰기 때문에 결제사와 우리 시스템이 항상 같은 값을 봅니다. 파티션 키는 주문 아이디를 써서 같은 주문의 메시지가 한 파티션에 들어가게 했고, 다섯 번 실패하면 DLQ 로 보내 매일 아침 확인합니다. 전환 후 중복 결제는 0건이고 재처리 지연이 평균 5분에서 12초로 줄었습니다.

### 7. 장애 대응

**이런 질문에** 장애 · 탐지 · MTTR · 사후 · 복구 · 온콜

결제사 응답이 느려지면서 워커가 묶여 주문 생성까지 밀린 장애가 있었습니다. 응답 시간 p95 알람이 먼저 울려 3분 만에 인지했고, 결제 승인을 비동기로 돌려 20분 만에 주문 생성을 복구했습니다. 저는 대응을 지휘하면서 결제사와 연락을 맡았고, 다른 두 명이 배포와 모니터링을 나눠 맡았습니다. 사후 조치로 결제 호출에 3초 타임아웃과 서킷 브레이커를 넣었습니다. 오류율이 1분간 30퍼센트를 넘으면 60초 동안 호출을 끊고 사용자에게 안내를 보여줍니다. 임계값은 평소 오류율이 0.3퍼센트라 그 100배를 기준으로 잡았습니다. 같은 유형의 장애는 이후 8개월간 재발하지 않았습니다.

### 8. 서비스 분리와 무중단 이관

**이런 질문에** 분리 · 마이그레이션 · 무중단 · 모놀리 · 이관 · 정산

정산 로직이 주문 테이블을 직접 읽고 있어서 주문 스키마를 바꿀 때마다 정산이 깨졌습니다. 분기당 두 번쯤 장애가 났습니다. 먼저 정산이 쓰는 컬럼을 API 로 감싸 읽게 바꾸고, 그다음 테이블을 분리했습니다. 한 번에 옮기는 안도 검토했는데 롤백 지점이 없어서 접었습니다. 무중단으로 하려고 이중 쓰기 구간을 2주 두고 양쪽 데이터를 매일 자정에 전량 대조했습니다. 첫 사흘은 0.02퍼센트가 어긋나서 원인을 잡았고, 이후 11일간 차이가 0 인 걸 확인한 뒤 읽기를 새 서비스로 넘겼습니다. 다운타임은 없었습니다.

### 9. 대용량 트래픽 병목

**이런 질문에** 트래픽 · 초당 · 1200 · 확장 · 스케일 · 처리량

피크 초당 1200 요청 구간에서 가장 큰 병목은 결제 승인 대기였습니다. 결제사 응답이 800ms 를 넘어가면 워커가 묶여 주문 생성까지 밀렸습니다. 결제 승인을 비동기로 돌리고 주문은 대기 상태로 먼저 만들어 응답했습니다. 타임아웃 3초를 넘으면 큐로 넘깁니다. 웹 서버 오토스케일만 늘리는 안도 해봤는데 DB 커넥션 풀이 먼저 한계라 효과가 없었습니다. 인스턴스를 두 배로 늘려도 처리량이 12퍼센트만 올랐습니다. 커넥션 풀 크기와 함께 조정하고 나서 초당 2100 요청까지 견디는 걸 부하 테스트로 확인했습니다.

### 10. 코드 리뷰와 온보딩

**이런 질문에** 리뷰 · 온보딩 · 협업 · 팀 · 이견 · 갈등

코드 리뷰는 규칙을 최소한으로 두는 데 신경 썼습니다. 리뷰어 두 명, 24시간 안에 응답, 지적할 항목을 체크리스트로 만들어 공유했습니다. 처음에는 형식적으로 흘러서 스타일 지적은 린터로 자동화하고 사람은 설계와 예외 처리만 보게 했습니다. 지표는 배포 후 롤백 건수 하나로 잡았습니다. 리뷰 수나 코멘트 수는 많다고 좋은 게 아니라 판단했습니다. 도입 전 두 분기 평균이 분기당 5건이었고, 도입 후 두 분기는 1건이었습니다. 같은 기간 배포 횟수는 오히려 늘었기 때문에 리뷰 효과로 봤습니다. 신입 세 명 온보딩할 때는 첫 2주를 리뷰어로만 참여하게 해 코드베이스를 먼저 읽게 했습니다.

### 11. 배포 파이프라인과 자동 롤백

**이런 질문에** 롤백 · 배포 · CI · CD · 파이프라인 · Docker

GitHub Actions 로 빌드하고 Kubernetes 에 롤링 업데이트로 배포합니다. 이미지는 멀티스테이지 빌드로 만들어 최종 이미지에 빌드 도구가 안 들어가게 했고, 그 결과 크기가 1.2GB 에서 340MB 로 줄어 배포 시간이 4분에서 90초가 됐습니다. 자동 롤백은 배포 후 5분간 두 지표를 봅니다. HTTP 5xx 비율이 1퍼센트를 2분 이상 넘거나, 응답 p95 가 직전 배포 대비 1.5배를 2분 이상 넘으면 이전 리비전으로 되돌립니다. 임계값은 평소 5xx 가 0.05퍼센트라 그 20배를 잡았고, 한 번에 튀는 값으로 되돌리지 않으려고 2분 지속 조건을 붙였습니다. 카나리 배포도 검토했는데 트래픽 분할 구성 부담이 커서 롤링에 자동 롤백을 붙이는 쪽을 택했습니다. 자동 롤백은 지난 1년에 3회 동작했습니다.

### 12. 모니터링 지표와 임계값

**이런 질문에** 지표 · 임계값 · 모니터링 · 알람 · 측정

알람은 사용자에게 보이는 지표를 우선으로 잡았습니다. 주문 생성 성공률, 주문 조회 p95, 결제 승인 오류율 세 가지입니다. CPU 나 메모리는 원인 파악용으로만 보고 알람은 걸지 않았습니다. 자원이 튀어도 사용자가 멀쩡하면 깨울 이유가 없다고 봤습니다. 임계값은 평소 값의 분포를 2주 모아서 정했습니다. 주문 생성 성공률은 평소 99.8퍼센트라 99.5퍼센트를 3분 이상 밑돌면 알람, 조회 p95 는 평소 180ms 라 500ms 를 5분 이상 넘으면 알람입니다. 처음에는 임계값을 촘촘하게 잡았다가 오탐이 주 20건 나와서 지속 시간 조건을 붙였고 주 2건 아래로 줄었습니다.

## 시연 중 주의

- 라포 질문(자기소개)은 채점하지 않고 80점 고정이다. 짧게 답해도 된다.
- 70점을 넘기면 꼬리질문이 안 붙는다. 수치와 판단 근거를 빠뜨리지 않는다.
- 같은 꼬리질문이 두 번 나오는 경우가 있다. 그때는 다른 각도로 답하면 넘어간다.
- 면접 종료를 누르면 리포트 생성에 2분 정도 걸린다. 화면이 멈춘 게 아니다.
- LLM 호출이 3회 실패하면 그 자리에서 오류가 난다. 답변을 다시 보내면 이어진다.
